## 实验一：HSH-64 码质量与桶分布（路线文档 M1 + M3.5）

**脚本**：`scripts/02_mvp_hsh64.py` ｜ **报告**：`results/mvp_report_mvp1.json`

**配置**：3109 词表，教师 = bge-large-zh-v1.5 (1024d)，学生输入 = 教师 PCA 截断至 512d，
Deep Hash MLP 512→512→52，500 epochs，Adam lr=1e-3，后处理 10 轮（neg_weight=1.0）。

### 结果

| 阶段 | Recall@1 | Recall@5 | **Recall@10** | Recall@20 |
|---|---|---|---|---|
| 后处理前 | 0.3133 | 0.5179 | 0.4988 | 0.2981 |
| **后处理后** | 0.2232 | 0.5885 | **0.7426** | 0.4816 |

> 口径：分母 \|P_i\|（参考实现口径）。若用论文式(35) 的分母 K 口径，后处理后 Recall@10 = **0.7128**。

**论文基准**：h256 = 0.7382，h512 = 0.7404（含后处理）。

### 距离几何（对比论文图 2）

| 量 | 本实验（后处理后） | 论文图 2 |
|---|---|---|
| 正样本对距离 | **9.17** ± 7.96 | ≈ 8 |
| 负样本对距离 | **26.08** ± 3.54 | ≈ 28 |
| 分离度 | **16.91 bit** | ≈ 18 |
| 随机基线 | 32.00 ± 4.00（64 位码理论值） | 26（52 位码理论值） |

> 随机基线差异是因为本文档的码是 64 位（feat+sim+abs），而论文图 2 只统计 52 位 sim 段。

### M3.5 桶分布验证（关键结论）

```
语义桶数            = 3075   (3109 个词)
最大桶              = 3      (后处理后为 8)
每桶 abs 槽位上限   = 256
超过上限的桶数      = 0
准完美哈希          = 可行
```

**这直接证实了路线文档 §3.3 的容量分析**：桶地址是 `(feat, sim)` 而非 `(feat, abs)`，
容量冗余极大，**不存在 v1 版本担心的容量危机**。3109 词规模下每桶平均仅 1.01 个 token。

### ⚠️ 配置偏差声明（影响可比性）

本机缺 bge-small-zh-v1.5 权重，**学生输入由 bge-large 的 PCA-512 截断模拟**，教师也是 bge-large。
学生输入与评测真值同源，**对指标有利**。因此 0.7426 与论文 0.7382/0.7404 **不能直接并列比较**。

本实验证明的是：**实现链路正确、码的几何可复现、桶结构成立**。
严格复现需等 bge-small 权重到位。

## 实验二：BNN 二值激活 + per-token 权重码（路线文档 M3.6 核心消融）

**脚本**：`scripts/03_bnn_ablation.py`

**任务**：字符级 next-char prediction（405 字符表，3109 词，2799/310 训练/验证）。

**要回答的问题**：`「权重码 + 共享基矩阵生成 per-token 权重」` 与 `「普通全局共享权重」`
在**同参数量、同数据、同训练步数**下谁更好？

### 2.1 等参数预算对照（d_model=128，40 epochs）

参数量由公式精确控制：`shared = embed(V_c·d) + [2·k·rank·(d + V_c)] + d`

| 模式 | 参数量 | val_loss | tok_acc | first_acc |
|---|---|---|---|---|
| **shared**（全局共享权重） | 524,629 | **3.9728** | **0.3094** | 0.1548 |
| code (k=8, rank=32) | 452,928 | 4.1618 | 0.2587 | 0.1548 |
| token_embed (td=64，经典 per-token) | 510,357 | 4.7827 | 0.2252 | 0.0452 |

### 2.2 高预算对照（d_model=128，k=64，20 epochs）

| 模式 | 参数量 | val_loss | tok_acc |
|---|---|---|---|
| shared (hidden=128) | 319,573 | **3.7742** | 0.2995 |
| code_no_param | 1,866,816 | 4.5233 | 0.5161 |
| code | 1,866,816 | 6.0050 | **0.5248** |

> 注意：此表中 shared 参数量少 5.8 倍，**不构成受控对照**，仅供参考。

### 2.3 结论（负面）

**在等参数预算的字符级 LM 任务上，「权重码 + 共享基」未能胜过全局共享权重。**

```
shared       val_loss 3.9728   tok_acc 0.3094
code         val_loss 4.1618   tok_acc 0.2587     → 劣于 shared
token_embed  val_loss 4.7827   tok_acc 0.2252     → 明显劣于 shared
```

两个有价值的相对结论：

1. **`code` 优于 `token_embed`** —— 说明「码 + 共享基」的结构化 per-token 参数
   确实优于经典的「每 token 一个自由向量」。这个排序是符合预期的。
2. **但两者都不如参数量相当的全局共享权重** —— 在**参数量不是瓶颈**时，
   per-token 参数化没有收益，反而引入了优化困难。

### 2.4 观察到的现象：per-token 权重不稳定

`code` 模式的验证指标持续震荡，与码翻转**无关**（关闭翻转后结果逐字节相同）：

```
epoch  4: val_loss=3.9811  first_acc=0.0806
epoch 12: val_loss=4.1351  first_acc=0.1548
epoch 20: val_loss=4.2882  first_acc=0.1548
epoch 24: val_loss=5.3595  first_acc=0.0000   ← 完全失稳
epoch 28: val_loss=4.1659  first_acc=0.1548
epoch 40: val_loss=4.1618  first_acc=0.1548
```

`first_acc` 在 0.0000 / 0.0516 / 0.1548 之间跳变，说明 per-token 权重矩阵在训练中不稳定。
根因：param 段只有 ±1 两种取值，梯度经 STE 直通后，`shadow` 的连续更新会不断改变 sign 模式，
使每个 token 的权重矩阵持续跳变 —— 优化景观本身是病态的。

## 实验过程中修复的三个真实 bug

记录以备复查，都是会静默产生错误结论的类型。

### Bug 1：后处理符号约定错配（一度误判论文出错）

**现象**：贪心后处理让召回从 0.4988 **崩到 0.036**，目标函数反向上升。

**排查**：穷举 4 种 Δ 公式变体 × 2 种目标函数定义，定位到 `2·se − rs` ≡ `ΔO_triu`，误差 8.3e-07。

**根因**：我把 `O_full = Σ_{i,j}` 与 `O_triu = Σ_{i<j}` 两种约定混用。
中途还一度"修正"了论文 Theorem 1 的符号 —— **那是错的**，论文是正确的，
我的原实现也是正确的，是"修正"引入了反转。

**修复**：`objective()` 与 `greedy_flip_deltas()` 统一为上三角约定。
**回归测试**：`scripts/selftest_post_optimize.py`（5 组用例，全通过）。

### Bug 2：`sign_patterns()` 用了无梯度的 `torch.sign`

**现象**：`code` 与 `code_no_param` 结果**逐字节相同**，param 段毫无作用。

**根因**：两处叠加 ——
① `param_shadow` 初始化为全零，`refresh_codes()` 后恒为常数；
② `sign_patterns()` 用 `torch.sign(param_shadow)`，该函数导数几乎处处为 0，
    梯度永远到不了 `param_shadow`。

**修复**：改用 `ste_sign()` 让梯度直通；`code` 模式初始化为非零随机值。
**注意**：后续又发现随机初值会打乱语义 mask，故最终改为**中性初值**
（全常数，等价于从 `code_no_param` 的几何出发，再由梯度引入 per-token 差异）。
中性初值把 `code` 的 val_loss 从 6.00 降到 3.12（8-epoch 对照）。

### Bug 3：`evaluate()` 与打乱后的 batch 错位

**现象**：`shared` 模式报 `Expected input batch_size (128) to match target batch_size (896)`。

**根因**：`make_batches` 会打乱顺序，而 `word_ids` 必须与批次内样本一一对应。
用打乱后的全局 `idx` 去索引会造成**静默的错误标签**（比崩溃更危险）。

**修复**：`evaluate()` 改为手动分批，`word_ids` 取自当前 chunk。

## 下一步的候选方向（尚未决断，留待作者判断）

MVP 的负面结论**不否定整套设计**，但明确了它的适用边界：
**per-token 权重码在「参数量不是瓶颈」时不占优**。它真正的卖点在另外三处，
而这些恰好是本 MVP **没有测**的：

1. **热更改 / 持续学习** —— 码是位，改一个 bit 即改权重，且 O(1) 可回滚。
   全局共享权重做不到这件事。**这是最该测的下一步。**
2. **模型编辑的可解释性与可逆性** —— 能读出改了哪几位、能翻回去。
3. **极端 per-token 预算**（如每 token 8 字节）—— 本实验给 code 的预算是 64 bit/词，
   若压到 8 bit，`token_embed` 会不可用而码方案仍可用。

建议下一阶段把评测目标从「LM 质量」换成「**热更改后目标域精度 / 非目标域遗忘量**」，
这才对应设计的真实目标。

Add MoE-style sparse FFN with code-driven routing; restructure documentation

MoE implementation
------------------
Instead of summing over all k basis matrices, each token activates only k':

    dense:  W_t = sum_{j=1..k}     s_j(t) * B_j
    MoE:    W_t = sum_{j in TopK'} s_j(t) * B_j

Routing is derived from the hash bits (expert_j = (h >> off_j) % k), so no router
network and no load-balancing loss are needed -- balance is structural.

Measured (base preset, k=16, k'=4, d_ff=256, rank=16):
  parameters        327,680 per layer = 15.6% of a standard FFN (2,097,152)
  load balance      normalised entropy 1.0000, all 16 experts used, max share 0.064
  sparse WRITE      editing one token changes only its own k'=4 experts;
                    0 other tokens affected. Blast radius k'/k, not 1.
  KV cache          identical to the growing-prefix path to 1.2e-06

New files:
  cabinet_bnn/bnn/moe_ffn.py      MoECodeFFN, MoEConfig
  scripts/selftest_moe_ffn.py     6 test groups, all passing
  scripts/20_verify_moe_scale.py  magnitude check against a standard FFN

Four defects found, all silent or near-silent
---------------------------------------------
1. Routing collapse from an uninitialised code table. WeightCodeTable.hash_code
   is a ZERO-initialised buffer; modulo routing on all-zeros selects the same
   experts for every token, so only 4 of 16 experts were ever used and nothing
   raised an error. Fixed with an explicit startup assertion plus a hard
   degeneracy check, and the trainer now initialises the codes and refuses to
   start on a collapsed router.

2. Weight-fold dimension mismatch. Folding used
   einsum("bk,bkro->bro", w, U_sel) with w of shape (B, ka); when ka happened to
   equal an output dimension the subscript bound to the wrong axis and still ran.
   The weight must be broadcast explicitly as (B, ka, 1, 1).

3. Initialisation magnitude wrong three times in a row (16x too large, then 1.3%,
   then 8.6% of the target). Each time the only symptom was "loss does not
   converge". Fixed by solving the down-projection bound analytically instead of
   adding guessed scale factors; the ratio to a standard FFN is now 0.58.

4. Sampling crashed at step 1000: token_ids.reshape(-1) in the FFN path ignored
   KV-cache decoding, where the block sees one query position but receives the
   full token sequence. Same root cause as the relation-gate cache bug: L is the
   number of queries in THIS forward pass, not the sequence length.

Experiment outcome, recorded honestly
-------------------------------------
The fine-tuning comparison does NOT support a conclusion about the mechanism
because it is not a fair test: the MoE run replaced a TRAINED FFN with a RANDOM
one, so at step 1000 it was still relearning an FFN (val_loss 4.5492 against the
control's ~2.97). Even if it had converged it could not isolate the MoE
mechanism. A fair comparison must train both sides from scratch or reset the FFN
on both sides. The run was stopped rather than reported as a result.
